1문서 목적

macOS의 $HOME 아래에서 프로젝트, 학습 자료, 개인 자료, 참고 자료와 임시 파일을 일관된 기준으로 배치하는 원칙을 기록한다.

파일은 받은 위치나 확장자가 아니라 실제로 사용할 위치에 둔다. 이것이 핵심 원칙이다. 다음 질문에 답할 때도 이 원칙을 적용한다.

  • 새 파일이나 디렉토리를 어디에 둘 것인가.
  • 여러 성격을 가진 자료는 어떤 기준으로 분류할 것인가.
  • 더 이상 사용하지 않는 항목은 어디로 이동할 것인가.
  • macOS 또는 애플리케이션이 관리하는 경로를 어떻게 구분할 것인가.
  • Inbox와 임시 공유 파일을 언제 정리할 것인가.

이 문서는 Git 저장소 내부 구조나 현재 파일 목록을 관리하지 않는다. 저장소 내부는 해당 프로젝트와 언어, framework의 규칙을 따른다.

문서에서는 실제 사용자명이 포함된 /Users/<username> 대신 ~를 사용한다. 현재 홈 경로는 다음 명령으로 확인한다.

sh
printf '%s\n' "$HOME"

출력은 /Users/<username> 형태여야 한다. 문서의 ~는 이 경로를 의미한다.

3전체 구성

안정적인 최상위 구조와 현재 용도가 확정된 하위 구조만 기준으로 관리한다.

~/
├── 01-personal/
│   └── 99-archive/
├── 02-work/
│   ├── 01-development/
│   ├── 02-study/
│   ├── 03-career/
│   └── 99-archive/
├── 03-reference/
│   ├── 01-code/
│   ├── 02-configs/
│   ├── 03-docs/
│   ├── 04-assets/
│   └── 99-archive/
├── 04-quickshare/
├── 99-archive/
├── Downloads/
├── Pictures/
│   └── screenshots/
├── Desktop/
└── Documents/ Movies/ Music/ Library/ Applications/ Public/

01-personal과 02-work 아래에는 지속할 용도가 실제로 생겼을 때만 하위 디렉토리를 추가한다. 현재 역할이 명확하지 않은 공용 infra 디렉토리는 만들지 않는다. 프로젝트에 필요한 DB와 container 구성은 해당 Git 저장소가 소유하며 개발환경 구성 원칙을 따른다.

4구성 원칙

4.1

받은 곳이 아니라 사용할 곳에 둔다

파일 형식이나 유입 경로보다 파일을 함께 사용하는 활동을 기준으로 배치한다.

  • 강의 자료와 그 강의를 따라 작성한 실습 코드는 02-work/02-study에서 함께 관리한다.
  • 프로젝트에서 사용하는 문서와 이미지는 필요하면 해당 Git 저장소 안에 둔다.
  • 여러 프로젝트에서 반복해서 참조하는 자료는 03-reference에 둔다.
  • 브라우저로 받은 파일은 Downloads에 계속 보관하지 않고 용도에 맞는 위치로 옮긴다.

같은 주제의 자료를 확장자에 따라 서로 다른 최상위 디렉토리로 나누지 않는다.

4.2

최상위 영역은 두 자리 번호로 정렬한다

직접 관리하는 최상위 디렉토리는 01부터 시작하는 두 자리 번호를 사용한다. 번호는 Finder와 terminal에서 자주 사용하는 영역을 위에 두고 역할을 예측할 수 있게 한다.

번호가 비어 있다는 이유만으로 새 영역을 만들지 않는다. 기존 영역과 다른 지속적인 책임이 확인될 때만 다음 번호를 사용한다.

4.3

99는 Archive로 예약한다

모든 계층에서 99-archive는 현재 사용하지 않는 항목을 시야에서 분리하는 용도로만 사용한다. 다른 의미로 99를 사용하지 않는다.

Archive 이동 여부는 고정된 미사용 기간으로 자동 판단하지 않는다. 현재 활동에서 사용하지 않는지, 원래 위치에서 계속 보일 필요가 없는지를 사람이 확인한 뒤 이동한다.

4.4

Archive는 삭제 대기실이 아니다

99-archive에 둔 항목은 검색과 재사용이 가능해야 한다. 재사용을 시작하면 원래 활성 위치로 되돌린다.

삭제가 목적이라면 Archive에 넣어 판단을 미루지 않는다. 삭제 대상과 사본, 복구 가능성을 확인한 뒤 별도의 삭제 판단을 수행한다.

4.5

Inbox와 보관 위치를 구분한다

Downloads와 Pictures/screenshots는 파일이 도착하는 Inbox다. 장기 보관 위치가 아니므로 파일이 쌓이기 전에 주기적으로 다음 중 하나를 선택한다.

  1. 실제 사용할 위치로 이동한다.
  2. 원본이 따로 있는 불필요한 사본이면 삭제한다.
  3. 아직 용도를 판단할 수 없다면 Inbox에 남기되 다음 정리 때 다시 판단한다.

마지막 선택을 반복해 별도의 pending, later, to-sort 디렉토리를 만들지 않는다.

macOS는 기본적으로 스크린샷을 Desktop에 저장한다. Pictures/screenshots를 Inbox로 사용하려면 저장 위치를 바꿔야 한다. Apple의 Screenshot 앱 안내에 따라 Shift-Command-5 → Options에서 ~/Pictures/screenshots를 지정한다. 디렉토리만 생성하고 저장 위치를 바꾸지 않은 상태를 정상 구성으로 보지 않는다.

4.6

Desktop을 보관 장소로 사용하지 않는다

Desktop에는 장기 보관 파일이나 작업 중인 프로젝트를 두지 않는다. 이렇게 하면 화면 공유와 파일 탐색 때 불필요한 노출이 줄고 파일 위치도 용도에 따라 판단하기 쉽다.

애플리케이션이 일시적으로 Desktop에 파일을 만들었다면 사용 후 실제 위치로 옮기거나 삭제한다.

4.7

macOS와 애플리케이션의 관리 경로를 존중한다

다음 경로는 macOS 또는 애플리케이션이 정한 구조를 우선한다.

  • Applications
  • Library
  • Documents
  • Movies
  • Music
  • Pictures
  • Public

애플리케이션이 이 경로에 library, cache 또는 전용 디렉토리를 만들었다면 동작을 확인하지 않은 채 이동하거나 이름을 바꾸지 않는다. 직접 관리하는 번호 디렉토리는 $HOME 최상위에 두고 macOS 예약 디렉토리 안에 같은 분류 체계를 중복해서 만들지 않는다.

4.8

디렉토리 깊이를 제한한다

직접 관리하는 일반 자료는 $HOME을 포함해 다섯 단계 안에 둔다. 여섯 번째 단계가 반복해서 필요하면 상위 분류가 지나치게 세분화되지 않았는지 검토한다.

다음 항목은 예외다.

  • Git 저장소 내부 구조
  • 개발 도구와 framework가 생성한 디렉토리
  • 애플리케이션이 자체 형식으로 관리하는 bundle
  • 다운로드한 뒤 내부 구조를 유지해야 하는 자료 묶음

Git 저장소는 디렉토리 배치 관점에서 하나의 leaf로 취급한다.

4.9

날짜가 의미 있는 파일만 날짜 형식을 사용한다

날짜가 검색과 정렬에 실제 의미가 있을 때 다음 형식을 사용한다.

yyyymmdd_keyword.ext

예시는 다음과 같다.

20260824_resume-backend.pdf

날짜가 필요하지 않은 파일에 생성일을 일괄적으로 붙이지 않는다. Git 저장소와 애플리케이션 관리 파일에는 이 규칙을 강제하지 않는다.

4.10

민감정보를 일반 파일 배치 대상으로 보지 않는다

password, API key, token과 2FA 복구 코드는 일반 디렉토리나 Git 저장소에 두지 않는다. SSH private key와 인증서 private key처럼 파일이어야 하는 자격증명은 해당 도구가 요구하는 위치와 최소 권한을 따르며 일반 자료와 섞지 않는다.

이 저장소에는 실제 자격증명이나 머신 고유 값을 기록하지 않는다.

5파일 배치 판정 순서

새 항목의 선례가 없다면 아래 질문을 차례로 확인하고 처음 해당하는 영역을 선택한다.

5.1남에게 보낸 뒤 지울 임시 사본인가

원본이 다른 위치에 있고 전달하려고 만든 사본이면 ~/04-quickshare에 둔다. 전달이 끝나면 사본을 삭제한다.

원본 자체를 전달하는 경우에는 04-quickshare로 이동하지 않는다.

5.2현재 사용하지 않는 항목인가

현재 활동에서 사용하지 않지만 보존할 가치가 있다면 원래 활성 위치의 99-archive로 이동한다.

예를 들어 개발 프로젝트는 ~/02-work/01-development/99-archive로 이동한다. 어느 영역에도 속하지 않는 최상위 항목만 ~/99-archive를 사용한다.

5.3남이 만들었거나 여러 영역에서 참조하는가

읽기 위한 외부 Git 저장소, 공통 설정 예시, 매뉴얼, 아이콘 묶음처럼 직접 만드는 작업보다 참조가 주목적이면 ~/03-reference에 둔다.

5.4개발·학습·구직 등 직업 활동인가

직업과 연결된 개발, 학습, 이력서와 면접 자료는 ~/02-work에 둔다. 파일 형식이 사진이나 동영상이어도 실제 사용 목적이 구직이나 발표라면 02-work가 소유한다.

5.5나머지 개인 자료인가

앞의 조건에 해당하지 않는 개인 기록, 사진과 취미 자료는 ~/01-personal에 둔다.

판정 흐름은 다음과 같다.

임시 공유 사본인가? ── 예 → 04-quickshare
        │ 아니오
현재 비활성인가? ───── 예 → 원래 영역의 99-archive
        │ 아니오
외부 제작·공통 참조인가? 예 → 03-reference
        │ 아니오
직업 활동인가? ─────── 예 → 02-work
        │ 아니오
        └──────────────→ 01-personal

6주요 경로별 역할

6.101-personal

개인 기록, 사진과 취미 자료를 관리한다. 하위 디렉토리는 실제 자료가 반복해서 생기고 독립된 역할이 확인될 때 추가한다.

6.202-work

직업과 연결된 활동을 관리한다.

경로역할
01-development직접 만들거나 유지보수하는 Git 저장소와 개발 프로젝트
02-study강의, 교재, 실습과 CS 학습 자료
03-career이력서, 포트폴리오, 면접과 구직 자료
99-archive현재 사용하지 않는 work 항목

프로젝트 종류에 따라 backend, frontend, python, sandbox 같은 중간 디렉토리를 미리 만들지 않는다. 필요가 분명하지 않으면 Git 저장소를 01-development 바로 아래에 둔다.

6.303-reference

직접 만드는 작업보다 여러 활동에서 반복해서 읽거나 가져다 쓰는 자료를 관리한다.

경로역할
01-code읽기와 비교가 목적인 외부 Git 저장소
02-configs여러 프로젝트에서 참조하는 설정 예시, editor 확장과 font
03-docsGuide, manual과 wiki 자료
04-assetsIcon, diagram 소재와 재사용 asset
99-archive현재 사용하지 않는 reference 자료

6.404-quickshare

메일, messenger 또는 외부 저장소로 보낼 임시 사본만 둔다. 원본 저장소나 장기 보관 위치로 사용하지 않는다.

6.5최상위 99-archive

01-personal, 02-work, 03-reference 중 어느 영역에도 속하지 않는 비활성 항목에만 사용한다. 해당 영역을 알 수 있다면 그 영역의 99-archive를 우선한다.

7경계가 바뀌는 사례

7.1읽기 위한 외부 저장소를 직접 수정하기 시작한다

읽기만 할 때는 03-reference/01-code에 둔다. 직접 유지할 commit을 만들기 시작하면 02-work/01-development로 이동한다.

7.2강의 실습이 독립 프로젝트로 발전한다

강의 진도를 따라가는 동안은 02-work/02-study에서 강의 자료와 함께 관리한다. 강의 범위를 벗어난 기능과 독립적인 목표가 생기면 02-work/01-development로 이동한다.

7.3Archive의 작업을 다시 시작한다

해당 99-archive에서 원래 활성 위치로 되돌린다. Archive 안에서 계속 작업하지 않는다.

7.4스크린샷을 실제 자료로 사용한다

Pictures/screenshots에 도착한 파일은 용도가 확정되면 해당 프로젝트, 발표 자료 또는 reference asset 위치로 이동한다. screenshot이라는 파일 종류가 최종 위치를 정하지 않는다.

7.5애플리케이션이 정해진 경로에 data를 만든다

Photos Library나 영상 편집 library의 위치를 애플리케이션이 관리한다면 그대로 둔다. 직접 만든 번호 체계로 이동하기 전에 애플리케이션이 공식적으로 경로 변경을 지원하는지 확인한다.

8설정 방법

초기화한 Mac에서는 현재 사용하기로 확정한 기본 경로만 생성한다.

sh
mkdir -p \
  ~/01-personal/99-archive \
  ~/02-work/01-development \
  ~/02-work/02-study \
  ~/02-work/03-career \
  ~/02-work/99-archive \
  ~/03-reference/01-code \
  ~/03-reference/02-configs \
  ~/03-reference/03-docs \
  ~/03-reference/04-assets \
  ~/03-reference/99-archive \
  ~/04-quickshare \
  ~/99-archive \
  ~/Pictures/screenshots

명령을 실행하기 전에 같은 이름의 파일이나 symlink가 없는지 확인한다. 기존 Mac에서는 구조를 통일하려고 파일을 일괄 이동하지 않고 각 대상과 애플리케이션 dependency를 먼저 확인한다.

~/Pictures/screenshots를 만든 뒤 Shift-Command-5로 Screenshot 앱을 열고 Options에서 이 디렉토리를 저장 위치로 선택한다. test screenshot을 하나 생성해 실제 저장 경로를 확인한 뒤 확인용 파일을 삭제한다.

9검증

9.1최상위 구조 확인

sh
find "$HOME" -maxdepth 1 -type d -print

다음을 확인한다.

  • 직접 관리하는 다섯 최상위 영역이 존재한다.
  • 99가 Archive 외의 의미로 사용되지 않는다.
  • Desktop에 장기 보관 파일이 없다.
  • Downloads와 Pictures/screenshots가 보관 폴더로 변하지 않았다.
  • 새 screenshot이 Pictures/screenshots에 저장되고 Desktop에 생성되지 않는다.
  • macOS 예약 디렉토리 안에 동일한 번호 분류 체계를 중복해서 만들지 않았다.

기본 디렉토리가 없거나 screenshot 저장 위치가 다르면 설정 방법을 따른다.

Desktop, Downloads 또는 Pictures/screenshots가 보관 위치로 사용되고 있다면 파일 배치 판정 순서를 적용한다.

9.2프로젝트 위치 확인

직접 관리하는 Git 저장소가 기본적으로 다음 경로 아래에 있는지 확인한다.

sh
find ~/02-work/01-development -maxdepth 2 -name .git -type d -print

Git 저장소 내부의 하위 구조는 이 검사 대상이 아니다.

직접 관리하는 Git 저장소가 기본 경로 밖에 있다면 개발·학습·구직 등 직업 활동의 배치 기준을 적용한다.

10이후 사용 및 유지보수

10.1새 디렉토리 추가

새 디렉토리는 다음 조건을 모두 만족할 때 추가한다.

  • 기존 디렉토리와 구분되는 지속적인 용도가 있다.
  • 같은 종류의 자료가 반복해서 생긴다.
  • 파일을 찾을 때 새로운 분류가 실제로 도움이 된다.
  • 번호와 이름만 보고 역할을 설명할 수 있다.

빈 번호를 채우거나 미래 사용을 예상하기 위한 디렉토리는 만들지 않는다.

10.2Inbox 정리

고정된 자동 삭제 주기를 두지 않되 파일이 쌓이기 전에 Downloads, Pictures/screenshots, 04-quickshare를 확인한다. 자동 정리 script는 사용하지 않는다.

10.3구조 변경

최상위 영역이나 번호를 변경할 때는 다음 항목을 함께 확인한다.

  • shell alias와 PATH
  • IDE의 최근 프로젝트와 workspace 경로
  • Git 저장소 remote와 script의 절대 경로
  • 문서 내부 링크와 예시 경로
  • 애플리케이션이 저장한 library 위치
  • 재설치 원칙의 생성 순서

11현재 범위 밖의 항목

이 문서가 다루지 않는 것 펼치기
  • 현재 $HOME의 실제 파일과 디렉토리 목록이 문서는 배치 원칙만 관리하고 머신의 현재 상태는 관리하지 않는다.
  • Git 저장소 내부의 언어·framework별 구조저장소 내부는 해당 프로젝트와 언어·framework의 규칙이 소유한다.
  • iCloud Drive, Time Machine과 외부 저장소의 backup 설계이 문서는 파일 배치만 다루고 backup 매체와 보존 방식은 다루지 않는다.
  • 애플리케이션 library의 내부 구조 변경애플리케이션이 관리하는 경로와 내부 구조를 임의로 변경하지 않는다.
  • API key, token과 private key의 보관 체계민감정보는 일반 파일 배치 대상으로 보지 않는다.
  • 파일 자동 이동, 자동 삭제와 정리 script현재는 수동 배치 원칙만 관리한다.
  • 역할이 확정되지 않은 공용 infra 디렉토리지속적인 용도가 확인되기 전에는 디렉토리를 미리 만들지 않는다.
